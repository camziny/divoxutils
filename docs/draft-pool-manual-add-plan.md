# Draft Rules: Auto-Ban Theurgist + Manual Pool Add

Two related draft changes: a small default-ban addition, and a larger change to let the draft creator add someone to a draft's player pool before they've joined. Both are implemented — see Status at the bottom.

## Request 1: Auto-ban Theurgist by default

**Current state.** `draftBans` already supports `source: "auto"` rows via `toggleAutoBanClass` (`convex/drafts.ts`), but nothing seeded them before this change — every "auto" ban was a manual creator click during setup. There's no separate "rules created" step: `createDraft` inserts the draft with default settings; setup is one continuous phase entered by `createDraft`, not a distinct follow-up mutation.

**Implemented.** `createDraft` now seeds a `source: "auto"` ban row for Theurgist, the same shape `toggleAutoBanClass` would produce. No schema changes.

## Request 2: Manually add a user to the draft pool

### Current state (verified against code)

- No "join a draft" flow before this change. The pool was bulk-inserted once, at draft creation, by the external Discord bot reading live voice-channel membership.
- `draftPlayers.discordUserId` is required and is the actual participant key throughout the stack, not just a display detail: captain fields (`team1CaptainId`/`team2CaptainId`) store it directly; turn authorization in `banClass`/`pickPlayer`/`pickRealm`/`setPlayerClass` gates on it; fight snapshots (`draftClassSnapshot.discordUserId`) require it non-null; stats/leaderboard aggregation and identity-link matching key off it; the bot's `/getDraftStatus` polling contract returns it verbatim and uses it as the literal Discord snowflake to move/DM players.
- Token delivery is narrow: `generateToken()` was only called once, inside `createDraft`'s loop. Only the draft creator and captains get an automatic DM; regular players rely on the bot-posted public link. A manually-added player needs a freshly minted token and a delivery path.

### What was built

**A single `removeDraftPlayer` mutation handles removal for every row**, regardless of how it got into the pool (bot-swept or manually added). Gated the same way every add path is — creator-only, `draft.status === "setup"` — which is also why it's safe to fully delete rather than soft-delete: nothing downstream (a pick, a ban, a fight snapshot) can reference a player until picking starts, and picking can't start until setup ends. The creator's own row is explicitly protected from self-removal, since deleting it would delete their own token and lock them out of every other creator-only action for the rest of the draft. Removing someone after they've been picked, banned against, or fought is a deliberately different, larger problem this doesn't attempt.

**Adding is one consolidated search**, not a raw-ID paste. Two data sources feed one search box in the "Manage players" panel:

1. **This server's draft history** (`knownPlayers` table + `searchKnownPlayers` query) — anyone who's drafted before in this Discord server, regardless of who created that draft. Guild-wide, not personal to the searching creator. A dedicated table, not a query over `draftPlayers` directly, populated by one shared `recordKnownPlayer` helper called from `createDraft`'s bulk insert and from the manual-add mutation (`addDraftPlayer`). Guild-scoped (`drafts.discordGuildId`), since divoxutils is multi-guild-capable — search must not leak one community's players into another's. A one-time `backfillKnownPlayers` migration seeded this from all historical `draftPlayers` rows at launch, since the table would otherwise start empty and stay useless until enough new drafts slowly repopulated it.
2. **Live Discord server members** (`searchDiscordGuildMembers`, a Convex `action`) — for anyone currently in the server who's never drafted before. Calls Discord's `GET /guilds/{id}/members/search` REST endpoint directly with the bot's token (stored as a Convex environment variable, `DISCORD_BOT_TOKEN`), matching on username or nickname by prefix. No privileged Discord intent needed — this is a plain REST call, not the gateway member cache. Scoped strictly to the draft's own guild; never a global Discord search.

Both are gated by the same creator-only check (`requireCreatorCaller`, verifying the caller's token against `draft.createdBy`) and exclude anyone already in the current pool. Results from both sources are merged into one list in the UI (deduped by Discord ID, history match preferred), rather than presented as separate tabs — a creator searching for someone shouldn't have to know or care which source will have them.

**Why search instead of raw Discord-ID paste.** Pasting a raw numeric ID has no way to catch a mis-copy until after the row already exists. Search — from either source — gives the creator a visual confirmation step (avatar + name in a result list) before committing, which directly serves the actual goal: making sure the row added is the person actually intended, not a fat-fingered ID pointing at someone else.

**Bot-repo changes** (`divoxutils-discord-bot/src/utils/draftWatcher.js`): none needed for a manually-added player to reach their team voice channel. Adding a player only works while `draft.status === "setup"` (`addDraftPlayer` in `convex/drafts.ts`), and the bot's team-move only ever fires once a draft is fully `complete` with the live fight started — a state setup always precedes and can never revert from. So a manually-added player is always part of the roster before the bot's team-move runs for the first time, and gets swept up in that single pass like everyone else.

A re-attempting variant of `shouldTriggerTeamMove` (tracking a `movedToTeamsPlayerIds` snapshot, re-running the move if any team-assigned player wasn't part of the last completed pass) was built and then removed. It was meant to cover a player added *after* team-move already fired — a scenario the paragraph above shows can't actually happen given the setup-only gate. Across three review rounds it produced three different infinite-retry bugs (roster-vs-team-assigned players, team-assigned-vs-confirmed-in-voice players, non-retryable per-member failures), each fixed by narrowing which players "count" — until it became clear the mechanism was solving a problem that doesn't exist for real, live drafts, at the cost of real, repeated bug risk. Reverted `shouldTriggerTeamMove` to its original one-shot gate (fires once per draft, purely off `lastMovePhase`). If a future change ever lets a player be added after team-move fires, this will need a real design pass, not another patch to "who counts as covered."

**No "share this link" step after adding.** An earlier version minted a token and showed the creator a copyable invite link after every add, on the assumption a manually-added player needed to "join" somehow. Checked every place this codebase gates an action on the caller's own identity (`callerPlayer.discordUserId === ...`) — it's always the draft creator, a team captain, or the coin-flip winner, never a plain non-captain player's own row. `setPlayerClass` even explicitly restricts to "captains or creator"; a regular player never sets their own class. So a search-added player has no self-service action to perform and never needed a link — they're just in the pool. `addDraftPlayer` still mints a token at insert time (needed if they're later made captain), but the existing bot captain-DM flow already delivers it from whatever row exists at that point, with no extra wiring. Removed the whole share-link UI; adding now just shows a success toast.

**Layout: the two toggle buttons are structurally independent of either panel's expanded content.** Both `ManagePlayersPanel` and `ClassRulesPanel` used to be single components that rendered their own trigger button *and* their own expanded body together, placed as siblings in one flex row. Whichever one had wide content — `ClassRulesPanel`'s old collapsed-state class-name summary, or later `ManagePlayersPanel`'s own search/results body once expanded — pushed the other button away, since a flex item's width includes everything inside it, not just the visible button. Reordering only fixed the specific case that had already been reported; the same bug reappeared the moment the *other* panel's content got wide instead. The real fix: each panel now exports a `use*State` hook (owns all its state) plus two separate presentational pieces, `*Trigger` (just the button) and `*Body` (everything else). `DraftBoard` calls each hook once, renders both triggers together in one row, and renders each body — full width, in normal document flow — below that row. Neither body can ever affect where the other trigger sits, regardless of which panel is open, in either order. The redundant collapsed-state class-name summary is still gone (replaced by a small count badge inside the "Class rules" button itself), since it was always redundant with the count badges the expanded panel's own tabs already show. Verified in an actual browser (Playwright) across all four combinations (both collapsed, either one open, both open) — button gap measured at exactly 8px in every case, no overlap with content below.

### What was considered and dropped

A "name-only placeholder" path — add someone with no Discord account at all yet, hand the creator a claim link, and resolve their identity automatically whenever they later sign up and link Discord — was fully designed and implemented (schema fields, ~6 Convex functions, an HTTP boundary, hooks into both existing identity routes, a claim-banner UI, bot-side handling), then removed after reconsidering the actual use case: these are **live, synchronous drafts**. Someone with zero Discord/divoxutils setup can't meaningfully join a draft happening right now regardless of how elegantly their eventual signup gets wired up later — by the time "later" would matter, the draft has moved on. The mechanism solved a problem that doesn't really occur for this product. Dropping it removed real complexity for no loss of anything actually useful; both a draft-history search and a live Discord search will always be strictly more useful than a placeholder for anyone who could plausibly join in time, since both require the person to already be reachable through Discord.

### Duplicate/typed-wrong-ID risk

Since adding is now search-and-select only (no raw-ID entry path), the original "creator fat-fingers an ID and adds the wrong real person" risk is closed by construction — there's no ID field to mistype. `addDraftPlayer`/`searchDiscordGuildMembers` also still guard against duplicates server-side (rejecting a `discordUserId` already in the pool) as defense against a stale search result at submission time.
